# opnsense_trust_ca (Resource)

Manage a root or intermediate CA, an OCSP signing certificate, or an imported CA
with the existing UUID-backed Trust owner. Existing configurations still create
an internal CA when no action is specified. A parent CA is referenced by its
`refid`, not its UUID.

Creation/operation intent is distinct from the action inferred by the API editor
on read. The editor's lifetime is a template default, not proof of actual
certificate validity. Description-only changes must not regenerate a CA. Change `action` to request
an operation, or change `operation_token` to deliberately repeat it; never use a
routine description edit as a generation trigger.

## Release-specific limitation

The provider retains its original unpatched OPNsense 26.7.8 key requirement.
The released 26.7.8_2 controller corrects that upstream condition, but keyless
provider support has not been enabled. Keyless import and metadata updates of
an existing keyless CA are rejected rather than generating a substitute key or
using raw configuration writes. Import with a matching certificate and key is
exercised by the 26.7.8_2 live matrix. Older firmware and OpenTofu execution
are not established by that proof.

## Sensitive material

API-returned private keys and supplied import keys are Sensitive. Sensitive does
not mean absent from Terraform state: use protected state storage and do not
publish raw plans, state, or debug logs. Public certificate payloads and readable
metadata are separate from generation intent.

Removing `action` or `operation_token`, or clearing them to empty values, never
requests generation/signing/reissue. A new nonempty token requires a nonempty
action; omitted-action defaults apply only to creation.

## Uncertain operation responses

An explicit update consumes its attempted action/token before sending the
non-idempotent request. If the response is lost or ambiguous,
`operation_status = "unknown"` retains that uncertainty with prior observations;
refresh does not invent proof of success or automatically repeat the operation.
Inspect the appliance securely and reconcile before deliberately changing the
operation token. A subsequent successful metadata edit is not proof that the
previous cryptographic operation succeeded. A failed create without a returned
UUID cannot fabricate an identity; inspect for an orphan before retrying.
Terraform Core can taint a failed create even when the provider retained a
confirmed UUID/key after readback failure. Inspect that UUID securely and
reconcile/import before accepting any replacement plan; do not blindly retry
creation or assume automatic recovery of a response-only key.

## Example Usage

```terraform
resource "opnsense_trust_ca" "example" {
  description = "Example root CA"
  common_name = "root.example.invalid"
  country     = "US"
  action      = "internal"
  lifetime    = 365
}
```

## Import

Import the CA UUID, then inspect a no-change plan before managing it. Import does
not recover original generation intent or prove that a CA was created with the
API editor's current defaults.

```shell
#!/usr/bin/env bash
# Purpose: Import an existing Trust CA UUID without changing appliance PKI.
# Usage: import.sh
set -euo pipefail
terraform import opnsense_trust_ca.example 00000000-0000-4000-8000-000000000001
```

For no-change adoption, start with the imported object's description and omit
creation/operation inputs (`action`, `operation_token`, lifetime and PEM inputs)
until after reviewing authoritative returned observations. The creation example
is not a no-change import configuration: supplying new explicit action intent
may deliberately request a cryptographic operation.
