## Intent

**Problem:** `pkg/opnsense.ClientConfig` already supports `RetryMax`, `RetryWaitMin`, and `RetryWaitMax`, but the provider hard-codes their defaults (3 retries, 1s minimum, 30s maximum). Operators with slow or transiently failing appliances cannot tune retry behavior, and the provider lacks the `retries` / `min_backoff` / `max_backoff` configuration and `OPNSENSE_RETRIES` / `OPNSENSE_MIN_BACKOFF` / `OPNSENSE_MAX_BACKOFF` environment variables exposed by the pinned reference provider.

**Approach:** Add three optional integer provider attributes measured in seconds, resolve them through the existing HCL-over-environment pattern, validate positive values, and pass the exact resolved values into `opnsense.ClientConfig`. Omitting them keeps today's defaults unchanged.

## Boundaries & Constraints

**Always:** HCL takes priority over environment variables. Omitted settings preserve defaults 3 / 1s / 30s. Resolved values map exactly into `ClientConfig`. Credential handling and the internal `MaxReadConcurrency` safety default (10) stay unchanged. Provider documentation and the unreleased changelog are updated in the same change.

**Never:** Do not expose `max_read_concurrency`. Do not add cross-field `min_backoff <= max_backoff` validation; the reference provider accepts any positive pair and `go-retryablehttp` clamps the computed backoff to the maximum. Do not change which HTTP status codes are retryable, the credential-validation request, or existing retry semantics. Do not make any new provider attribute required.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Omitted | All three HCL values null and env vars unset | Resolved retry fields are zero; `NewClient` applies 3 / 1s / 30s | N/A |
| HCL only | `retries = 5`, `min_backoff = 2`, `max_backoff = 10` | `ClientConfig` receives 5, 2s, 10s | N/A |
| Env only | Env vars set, HCL null | Env values are used | N/A |
| Both | HCL and env set to different values | HCL values win | N/A |
| Unknown HCL | HCL value unknown, env set | Env fallback is used, matching existing helpers | N/A |
| Invalid env | Env is empty, non-numeric, zero, negative, or above the allowed bound | Treat as unset; defaults apply | No diagnostic, matching existing env helpers |
| Invalid HCL | `retries < 1`, `retries > 2147483647`, or backoff `< 1` | Terraform configuration validation fails | Attribute validator diagnostic |
| Min above max | `min_backoff = 30`, `max_backoff = 1` | Values pass through unchanged | Client clamps backoff to the maximum |

## Design Notes

- Backoff units are whole seconds, matching the reference provider. All three attributes use a `1..2147483647` bound: this mirrors the reference retry bound, prevents `time.Duration` overflow when multiplying by `time.Second`, and is far above any practical retry window.
- Invalid or non-positive environment values are treated as unset rather than failing. This follows the existing `envOrBoolValue` convention and the reference provider's parse-error-to-default behavior.
- `min_backoff > max_backoff` is accepted. `go-retryablehttp` clamps each computed wait to `RetryWaitMax`, so rejecting the pair would add behavior the reference provider does not have.
- `resolvedConfig.toClientConfig()` keeps credential fields and retry fields in one explicit mapping, making the handoff unit-testable without exposing client internals.
